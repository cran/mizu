This article covers deployment settings for mizu processes, and what happens when one of them dies.

Deploying on Linux

mizu requires Linux kernel 5.3 or later. The death of a peer is detected through pidfd_open, with no fallback for older kernels.

On Linux, POSIX shared memory is /dev/shm, a bounded tmpfs mount. Everything mizu creates must fit in it: the pool and channel regions, plus a region per payload too large for a slot. Container runtimes set it to 64 MB by default. Use docker run --shm-size=4g, or the equivalent in your orchestrator. Size it to your peak in-flight payload traffic.

Linux memory allocator

This section applies only to Linux with glibc.

When mizu starts a channel peer or a pool worker, that process changes two settings of the C memory allocator. It raises the mmap threshold to 32 MB and the trim threshold to 128 MB. This keeps large payloads in fast memory. Without this change, glibc asks the kernel to map and unmap each large payload, and that work is slow.

Your own R process does not change. If you want the same settings there, set them before R starts:

export GLIBC_TUNABLES=glibc.malloc.mmap_threshold=33554432:glibc.malloc.trim_threshold=134217728

If you have set GLIBC_TUNABLES, mizu respects your values.

Garbage collection boundary

Received zero-copy views pin shared memory that R’s garbage collector cannot see. To return those loans promptly, the receive functions and worker task boundaries run a minor garbage collection once 8 MiB of released view memory has accumulated. This costs about 0.2 ms when it runs, and is the largest latency outlier in the system.

Set options(mizu.gc_boundary) before loading the package to change the threshold (in bytes). 0 disables the boundary collection, leaving loan release to R’s own garbage collection schedule.

When a process dies

The death of any participant is detected as soon as the operating system reports it, with no heartbeats and no polling. Every process holds a lock that the kernel releases when the process exits, for any reason. That release is what the other processes detect. A dead worker fails exactly the tasks that it claimed, and collecting one of them raises an error. The surviving workers consume the work still queued to the dead worker. On a channel, the survivor sees mizu_peer_gone. This split holds across the whole API. Transport states (nothing yet, no room now, stream over) are returned as sentinel values for the receiving loop to handle. A request that can never be satisfied raises a classed condition instead (see ?mizu_error): the task’s own error, a cancelled task, a dead worker, or a child that failed to start.

A crashed process cannot clean up after itself. mizu_prune() removes the shared-memory regions that dead processes leave behind. Regions of running processes are never touched.
